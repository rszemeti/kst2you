# Internationalisation (i18n) guide

How user-facing text works in the KST2You web app (`docs/`), and the exact
steps for changing it. Follow these patterns for any new or edited UI text.

**Before you finish any change that touches UI text, run:**

```sh
node scripts/check_i18n.js
```

It must print `0 error(s)` and exit 0. Treat warnings as errors unless the
line is a deliberate exception (see [Dynamic keys](#dynamic-keys)).

---

## 1. Files

| File | Role |
|---|---|
| `docs/assets/i18n/en.js` | English table. **Source of truth for every key.** |
| `docs/assets/i18n/fr.js`, `de.js` | French and German tables. Same keys as `en.js`. |
| `docs/assets/js/i18n.js` | Runtime: picks the language, translates tagged HTML, exposes `I18n`. |
| `docs/index.html` | Static markup, tagged with `data-i18n*` attributes. Loads the tables and runtime. |
| `scripts/check_i18n.js` | Consistency checker (Node, no dependencies). |

Load order in `index.html` is required: all `assets/i18n/*.js` tables, then
`assets/js/i18n.js`, then the app modules (`Kst.js`, …). The checker
enforces this. Because the runtime loads first, app code may call `I18n.t()`
at the top level, for example in a `const` array.

Each table is a flat object of dotted keys:

```js
window.KST_I18N = window.KST_I18N || {};
window.KST_I18N.en = {
  "nav.away": "Away",
  ...
};
```

## 2. Runtime behaviour

- **Language choice:** a value saved in `localStorage['kst2you_lang']`, else
  the first browser language (`navigator.languages`, full code then base code)
  that has a table, else `en`.
- **Lookup:** `I18n.t(key)` tries the current language, then `en`, then
  returns the key itself. A missing translation shows English, but the checker
  still reports it as an error.
- **Static HTML** is translated **once**, at load, before any app module runs.
  Nothing re-translates later.
- **Changing language** saves the choice and reloads the page. The reload
  drops the KST connection. The `<select data-lang-select="confirm">` picker
  in Settings asks before reloading while connected, and the login dialog
  picker (`data-lang-select`) switches immediately. Both are filled
  automatically from the loaded tables.

### API

```js
I18n.t('key')                         // plain text
I18n.t('key', { call: 'G1YFG' })      // replaces {call} in the string
I18n.h('key', { ... })                // same, HTML-escaped (& < > " ')
I18n.lang()                           // current code, e.g. 'fr'
I18n.languages()                      // loaded codes
I18n.setLang('de')                    // save and reload
I18n.apply(rootElement)               // translate data-i18n* inside a subtree
```

## 3. Keys

- **Format:** `area.name` in lowerCamelCase segments, e.g. `scatter.noAircraft`,
  `settings.remote.confirmDelete`, `contest.col.dist`.
- **Pick the area** from the existing prefixes, which are grouped in this order
  in `en.js`: `nav lang conn login tabs col chat chatPopup inbox users map beacon spot prop scatter aircraft rotator opensky settings remote cloud contest admin about bands locatorPrompt location cq setName profile dxlog common`.
  Add a new prefix only for a genuinely new feature area.
- **Reuse before adding.** `common.*` holds generic words (`common.cancel`,
  `common.close`, `common.send`, `common.save`, `common.loadingEllipsis`,
  `common.networkError`, `common.callsign`, `common.frequency`, …), and `col.*`
  holds table column headers. Use these when the meaning really is identical.
  Use a separate key when the same English word might need different
  translations in different places.
- **Placement:** insert the new key inside its prefix group in `en.js`, then at
  the same position in every other table. Keep all tables in the same order.
- **No unused keys.** If you remove the last use of a key, delete it from every
  table. The checker flags unused keys in `en.js`.

## 4. Adding text in HTML (`docs/index.html`)

Leave the English text in the markup as the no-JS fallback, and make it
**identical** to the `en.js` value. Then tag the element:

| Attribute | Sets | Use for |
|---|---|---|
| `data-i18n="key"` | `textContent` | Elements that contain only text |
| `data-i18n-html="key"` | `innerHTML` | Text with inline links/markup (value must be trusted HTML) |
| `data-i18n-title="key"` | `title` | Tooltips |
| `data-i18n-placeholder="key"` | `placeholder` | Inputs |
| `data-i18n-aria-label="key"` | `aria-label` | Icon buttons, close buttons |
| `data-i18n-alt="key"` | `alt` | Images |

Examples (all real):

```html
<button class="btn btn-sm btn-outline-light ms-2" id="logOffButton" type="button" data-i18n="nav.logOff">Log Off</button>

<!-- Icon plus text: wrap ONLY the text, or textContent would delete the icon. -->
<i class="bi bi-gear me-1"></i><span data-i18n="tabs.settings">Settings</span>

<!-- Text next to a value element: wrap the label separately. -->
<span><span data-i18n="scatter.lastScan">Last scan:</span> <span id="scatter-last-scan">—</span></span>

<!-- Attributes, can be combined on one element. -->
<input id="chatPopupMessageInput" placeholder="Write your message" data-i18n-placeholder="chatPopup.messagePlaceholder">
<button class="btn-close" aria-label="Close" data-i18n-aria-label="common.close"></button>

<!-- Inline link: translate the whole paragraph as HTML. -->
<p class="small mb-0" data-i18n-html="login.registerHint">To use this service you need a KST account. You can register <a href="http://www.on4kst.info/chat/register.php" target="_blank">here</a>.</p>
```

Rules:

- **`data-i18n` only on elements with no child elements.** Otherwise wrap the
  text in a `<span>` and tag the span.
- **`data-i18n-html` values replace the element's children**, so any element
  inside the value (for example `<span id="userCount"></span>` in
  `about.privacy`) is recreated from the table. Every translation must keep the
  same tags and `id`s. The checker compares tags and ids against `en`.
- **Text that JS overwrites later** (status labels such as `#connState` or
  `#scatter-status`) may still carry `data-i18n` for its initial value. The JS
  that changes it must use `I18n.t()` too.
- **Do not tag** brand names (KST2You, RainViewer, PstRotator), units (km, MHz),
  band labels (`23cm · 1296 MHz`), placeholder dashes (`—`), or numbers.

## 5. Adding text in JavaScript (`docs/assets/js/*.js`)

Never hard-code user-facing English. Use `I18n.t` when the result is used as
text, and `I18n.h` when it is concatenated into an HTML string.

| Destination | Use |
|---|---|
| `el.textContent = …`, `$(…).text(…)`, `el.title = …`, `$(…).attr('placeholder', …)` | `I18n.t` |
| `alert(…)`, `confirm(…)`, `prompt(…)`, `new Error(…)` shown to the user | `I18n.t` |
| `$('<option>', { text: … })`, Google Charts column labels | `I18n.t` |
| `el.innerHTML = '…' + X + '…'`, `$(…).html(…)`, `.append('<…>')`, template literals building markup, attribute values inside markup | `I18n.h` |

Real examples:

```js
$('#connState').text(I18n.t('conn.connected'));
alert(I18n.t('contest.restoreFailed', { reason: resp ? resp.message : I18n.t('common.networkError') }));
if (!confirm(I18n.t('contest.confirmUnmark', { call: cs }))) return;

list.innerHTML = '<div class="s-empty"><i class="bi bi-search me-1"></i>' + I18n.h('scatter.noAircraft') + '</div>';
' title="' + I18n.h('scatter.checkPathTo', { locator: row.locator }) + '">✈</button>'
`<tr><td>${I18n.h('aircraft.info.speed')}</td><td>…</td></tr>`
```

Rules:

- **Keys are string literals:** `I18n.t('a.b')`, never `I18n.t(prefix + name)`.
  The checker finds keys by literal match.
- **Whole sentences, with placeholders.** Put variable parts in `{name}`
  placeholders and pass them as params. Never join translated fragments into a
  sentence, because word order differs between languages:
  - ✗ `I18n.t('scatter.entry') + ' ~' + mins + ' min'`
  - ✓ `I18n.t('scatter.entryIn', { mins: Math.round(p.minsToEntry) })` with `"Entry in ~{mins} min"`
- **Use `I18n.h`, not your own escape around `I18n.t`.** Don't write
  `escHtml(I18n.t(…))` or `escapeChatHtml(I18n.t(…))`.
- **Never branch on displayed text.** Compare state values (`'worked'`,
  `connectState`, option `value`s), never the translated label.
- **Line breaks in `confirm`/`prompt`** are `\n` inside the table value.
- **Add the key** to `en.js` and to every other table (section 6) in the same
  change.

### Dynamic keys

A helper that receives a list of keys can't use a literal at the call site.
The only current one is `_th(keys)` in `ContestLog.js`, which builds `<th>`
cells:

```js
_th(['col.call', 'col.locator', 'contest.col.dist', 'col.time', ''])   // '' = empty cell
```

The checker understands `_th([...])` arrays and ignores the helper's own line
because it is marked `// i18n-dynamic`. If you add a similar helper, mark its
`I18n.t/h(variable)` line `// i18n-dynamic` **and** extend the key-collection
regexes in `scripts/check_i18n.js` so its call sites are still checked.

## 6. What must NOT be translated

Leave these in English, and in their current form:

- **Text sent to other stations or servers:** the locator autoresponder reply
  (`loc: … beam: …` in `Kst.js`), `AS!` plane alerts and `/CQ` messages
  (`scatter.js`), anything passed to `sendMsg(...)`, and spot payloads.
- **Text matched against server output:** for example `"Your name is now"`,
  `"Invalid first name"` and `"Available DX clusters"` in `procChatMessage`,
  and `"Java login"`. These come from ON4KST in English.
- **Messages from servers** displayed as received (`data[2]` login errors,
  `resp.message` from cloud functions). Only the fallback text you supply is
  translated.
- **File formats:** CSV headers and the EDI/REG1TEST export (`ContestLog.js`).
  Other tools parse these.
- **Identifiers:** storage keys, cookie names, CSS classes, element ids, action
  names (`contestSave`, …), option `value`s, propagation mode codes (`TR`,
  `AS`, …; translate only their display `text`).
- **Developer output:** `console.*`, internal `throw`s that are never shown
  (Maidenhead parsing, RainViewer/aircraft-feed transport errors), and test
  fixtures (`ChatInbox.test()`).
- **Names and units:** KST chat group names (`chatGroups` in `Kst.js`), band
  labels, brand names, units.

If you're unsure whether a string reaches the user, trace where it ends up. If
it reaches the DOM, `alert`, `confirm` or `prompt`, translate it.

## 7. Writing translations

- **Translate the whole value; keep its structure:**
  - every `{placeholder}`, spelled exactly as in English;
  - all HTML tags, attributes, `href`s and `id`s in `data-i18n-html` values;
  - HTML entities: `&amp;` stays `&amp;` in `data-i18n-html` values;
  - `\n` line breaks in confirm/prompt text;
  - leading symbols: `✓ ✗ ⊕ ✈ ⟳ ☁ ▸ ⚠`.
- **Amateur radio terms** follow normal ham usage in each language:

  | Concept | fr | de |
  |---|---|---|
  | callsign | indicatif | Rufzeichen |
  | locator | locator | Locator |
  | beacon | balise | Bake |
  | rotator | rotor | Rotor |
  | worked / skip | contacté / ignoré | gearbeitet / übersprungen |
  | report | report | Rapport |
  | scatter modes | keep "aircraft scatter", "meteor scatter" | Aircraft-Scatter, Meteorscatter |
  | QSO, RST, DX Cluster, CQ, Spot | unchanged | unchanged |

- **Style:**
  - **French:** « » quotes, typographic ’, a space before `:` `?` `!`.
  - **German:** „“ quotes, informal *du* (as used in the existing table),
    `z. B.`.
- **Brevity:** keep it short where space is tight (tab labels, table headers,
  buttons, the navbar). Abbreviate as in the existing tables (`Entf.`, `Dist.`).
- **Quotes inside values:** values are JSON-style double-quoted strings, so
  escape `"` as `\"`. Prefer the language's own quote marks.

## 8. Adding a new language

1. Copy `docs/assets/i18n/en.js` to `docs/assets/i18n/<code>.js`. `<code>` is
   a lowercase ISO 639-1 code, matching the base of a browser language tag
   (`es`, `it`, `nl`, …).
2. Change the header comment and the last line to
   `window.KST_I18N.<code> = {`, then translate every value (section 7).
3. In `docs/index.html`, add `<script src="assets/i18n/<code>.js"></script>`
   next to the other tables, **before** `assets/js/i18n.js`.
4. In `docs/assets/js/i18n.js`, add the native name to `NAMES`, e.g.
   `es: 'Español'`.
5. Run `node scripts/check_i18n.js`.

Both pickers list the new language automatically. Browsers whose preferred
language matches `<code>` select it by default.

## 9. Checklist for any UI-text change

1. New or changed English text has a key in `en.js`, in the right prefix group.
2. The same key and a real translation are in **every** other table, at the
   same position.
3. HTML is tagged with the right `data-i18n*` attribute, and its fallback
   English matches `en.js`.
4. JS uses `I18n.t` for text and `I18n.h` inside HTML strings, with literal
   keys and `{placeholders}`, and no logic depends on translated text.
5. Nothing from section 6 was translated.
6. `node scripts/check_i18n.js` prints `0 error(s), 0 warning(s)`.
7. `node --check <file>` passes for every JS file you edited.

## 10. Checker reference

`node scripts/check_i18n.js` reports:

| Message | Fix |
|---|---|
| `key "x" is not defined in en.js` | Add the key to `en.js` and every other table, or fix the typo at the use site. |
| `en.js: key "x" is never used` | Remove it from all tables, or restore the use you deleted. |
| `<lang>.js: missing key "x"` / `extra key "x"` | Make the table's keys match `en.js` exactly. |
| `placeholders differ` | The translation lost, added or misspelled a `{placeholder}`. |
| `HTML tags differ` / `element ids differ` | Restore the markup from the English value. |
| `does not load …` / `must load before assets/js/i18n.js` | Fix the `<script>` tags in `index.html`. |
| `NAMES has no entry` | Add the language's native name to `NAMES` in `i18n.js`. |
| `WARNING: non-literal key` | Use a literal key, or see [Dynamic keys](#dynamic-keys). |

It reads keys from `data-i18n*` attributes in `index.html`, from
`I18n.t('…')` / `I18n.h('…')` and `_th([…])` in `docs/assets/js/**/*.js`, and
from `t('…')` inside `i18n.js`. Whole-line comments are ignored.
